# 待办

**这是开放事项的唯一清单。** 修完就把条目删掉，不要在这里堆「已完成」——
做过什么看 git 历史，这份文件只回答「现在还欠什么」。

每条尽量写清三件事：**现状**（症状或缺口）、**证据**（怎么知道的，日志/实测/代码位置）、
**方向**（已经想到的修法，没想清就写没想清）。没有证据的猜测不要进这份清单 ——
这个项目在"读码推测根因"上已经错过好几次，宁可写「待确认」。

## A. 已实现但没在真机目标配置下验证过

这一组最该先处理：代码写了、单测绿了，但**没有真机证据**，所以不能当成已修。

### A1. 「允许说话打断她」关闭时，她到底会不会被打断

- **现状**：v2.0.1 把这条改成了「她一开口就把服务端 VAD 整个关掉，说完再恢复」
  （见 `RealtimeSession` 的 `shieldWhileSpeaking` / `vadSuspended`）。单测覆盖了
  VAD 是否真被关掉、麦克风上行是否真停了。
- **证据**：三轮真机测试**一次都没落在目标配置上** —— 日志里第一轮是
  `listening=false`（持续聆听关着，VAD 本来就是 null），第二、三轮都是
  `interruptible=true`。所以「关掉开关后她不被打断」这件事至今没被观察到过。
- **方向**：按 `docs/DESKTOP_QA.md` 跑一次：右键确认「持续聆听」打钩、
  「允许说话打断她」**不打钩** → 问她一个能说两三句的问题 → 她说到一半时开口说
  三四秒 → 她应该把话说完。从终端启动 `.app` 看 stderr，日志里应当出现
  `vad: 不可打断 —— 已关掉服务端 VAD（她说完再开）`，并且她说话期间**不该**再出现
  `vad: 服务端检测到人声开始`。

### A2. 30 分钟会话轮换

- **现状**：到期静默重建、带上下文摘要过去；v2.0.1 之后还多了「轮换前最多等她
  说完 60 秒」的逻辑（`waitUntilQuiet`）。
- **证据**：从没坐等过 30 分钟。两条逻辑都只有单测。
- **方向**：挂机等一次，或者临时把 `ROTATE_MARGIN_MS` 调大来提前触发。要确认的是：
  重建对用户不可见、摘要真的带过去了（她不会从头自我介绍）、以及她正说话时
  不会被切在半句上。

### A3. `response.thinking.delta` 从未被观察到

- **现状**：处理代码在，由它驱动「思考」表情。
- **证据**：任何探针、任何真机日志里都没出现过这个事件。
- **方向**：要么抓到它、要么确认服务端不发，然后决定是删掉这条路径还是改由别的
  信号驱动思考表情。**现在它属于「写了但从未执行过」的代码。**

### A4. 录屏权限被拒的分支

- **现状**：本机已授权，没法撤销来测。
- **证据**：未验证。
- **方向**：换个账号或新机器测。关键问题是 1×1 探针在未授权时**是否会弹系统弹窗**
  —— 如果会弹，`screen_permission_status` 就不能在启动时投机调用。

### A5. 混合模式（realtime 做交互 + chat 承担智能）

- **现状**：可行性分析写在 `docs/BRAIN_MODES.md`，结论是「有条件可行，但得先验证
  realtime 能不能被稳定保持住」。接口已按 `PetBrain` 抽好，**没有实现**。
- **方向**：先把 A2 验了（30 分钟轮换是否真的无感），那是「能不能稳定保持」的前提。

## B. 已定位的小缺陷

### B1. `enableMic()` 在启动路径上被调了两次

- **现状**：日志里 `mic: 会话已开启麦克风（持续采集）` 每次启动都出现**两条**。
- **证据**：`Brain.start(true)` → `doStart` → `RealtimeSession.start(true)`，
  后者末尾 `if (continuous) await this.enableMic()` 开了第一次；回到
  `Brain.start` 的 `if (withMic) await this.session?.enableMic()`（`Brain.ts:115`）
  又开了第二次。`MicStream` 有入口守卫，所以不会真的开两路麦 —— 功能没坏，
  但多一次 `getUserMedia` 往返，而且日志里一直有两条噪音。
- **方向**：`Brain.ts:115` 那一行是为「会话已经在了，之后再补开麦」准备的
  （先打字起会话、再从托盘开语音）。只在**会话本来就存在**时调它即可，
  不要在刚 `doStart` 过之后再调一次。

### B2. 挂机时反复重连，每次重推完整 session 配置

- **现状**：服务端会掐掉长时间没动作的会话，消息是 `too long without operation`。
  我们自动重连，对用户没有影响（v2.0.1 起这条已不弹报错气泡）。
- **证据**：一次挂机的日志里刷了约 10 条该错误，每条后面跟一次
  `session: listening=... turn_detection=...`，也就是重连后重推一遍完整配置
  —— 而 instructions 并不短。
- **方向**：空闲时主动关掉 socket、等用户说话/打字时再连；或者查服务端是否支持
  某种 keepalive。**先确认这件事到底有没有成本**（额度？延迟？）再决定值不值得做。

## C. 分发与平台

### C1. 只支持 Apple Silicon

- **现状**：产物是 `aarch64` 单架构，Intel Mac 跑不了。
- **方向**：装 `x86_64-apple-darwin` 目标后 `tauri build --target universal-apple-darwin`。

### C2. ad-hoc 签名、未公证

- **现状**：`signingIdentity: "-"`，`spctl -a` 返回 `rejected`，首次打开要右键 →
  打开，或 `xattr -dr com.apple.quarantine`。
- **方向**：Apple 开发者证书 + notarize。属于「要不要以正式产品分发」的决定，
  不是纯技术问题。

### C3. TCC 授权绑定代码签名，重新编译即失效

- **现状**：ad-hoc 签名每次重建身份都变，macOS 把它当成新应用，之前授过的麦克风/
  录屏权限会失效。症状是「麦克风自检通过但说话没反应」。
- **证据**：设置里的麦克风自检已经把这条写进了建议文案。
- **方向**：开发期没有好办法（这是 TCC 的设计）。**演示前的正确顺序是：构建最后
  一版 → 在那个产物上授权 → 不再重编。** 真要根治得走 C2。

### C4. Android 只预留了接缝

- **现状**：`Desktop` 契约 + 按 target 分组的依赖 + 分平台 capabilities 都在，
  **没有做过任何 Android 构建**。
- **方向**：真要做的话第一步是给 `Desktop` 契约写一个 Android 实现，
  并确认 Tauri 的 Android 支持能不能满足「透明置顶窗口」这个前提 —— 很可能不能，
  那样整个交互形态都要重新设计（悬浮窗 vs 桌宠）。

## D. 协议缺口 / 需要向阶跃确认

### D1. `turn_detection` 没有「要 VAD 断句但不要自动开回合」的字段

- **现状**：这是「不可打断」整件事麻烦的根源。服务端 VAD 一检测到人声就会提交并
  开新回合，而新回合一开就把她上一轮的生成丢掉。协议里（`shared/realtime.ts` 的
  `SessionConfig.turn_detection`）没有任何字段能表达「只要断句，别自动回复」。
- **证据**：v2.0.0 试过「收到人声检测后清空服务端缓冲」，真机日志证明来不及 ——
  服务端在发出 `speech_started` 那一刻就已经开了回合。现在只能靠**整个关掉 VAD**
  绕过（见 A1）。
- **方向**：向阶跃确认有没有未公开的字段（OpenAI Realtime 有
  `turn_detection.create_response: false`），或者提个需求。有了它这段逻辑可以
  大幅简化，也不用在她说话期间把用户的声音整个丢掉。

### D2. ASR 的 `.failed` 事件我们定义了但从未实测到

- **现状**：`conversation.item.input_audio_transcription.failed` 在
  `shared/realtime.ts` 里有定义，处理逻辑是把用户气泡收掉。
- **证据**：**没有观察到服务端真的发它。** 定义它的理由是：不定义就会被降级成
  `unknown` 然后 `console.debug` 掉，而它恰好是「用户气泡永久卡住」的一条路径。
- **方向**：留着（成本三行），但别把它当成已验证的协议事实。

## E. 测试覆盖缺口

都是「需要 DOM 或真实计时器」的部分，刻意没有为了可测而改结构。

- **E1** `syncSession` 里 `syncedRef` 的实际去重时序（右键菜单直接调用 + 广播回来
  撞在一起时，后到的那次应当退化成空操作）
- **E2** 全局 `keydown` 监听的挂载/摘除
- **E3** `showNotice` / `showError` 的 timer 行为（重入先 clear、卸载时清）
- **E4** 新回合开始时清掉上一句气泡的那个边沿 —— 依赖事件顺序，要跑完整 React + 大脑

方向：这四条要么引入一个 DOM 测试环境（jsdom / happy-dom），要么接受它们由人工
验收覆盖（`docs/DESKTOP_QA.md`）。**不建议为了凑覆盖率把 `App.tsx` 拆得更碎** ——
能脱开 DOM 的判断已经抽到 `ui/uiState.ts` 了。

## F. 可用性

### F1. Esc 打断只在 Step酱 是当前应用时有效

- **现状**：桌宠窗用 `ActivationPolicy::Accessory`，平时不抢键盘焦点，所以全局
  `keydown` 收不到。README 和设置里的文案已如实说明「长按才是可靠的打断方式」。
- **方向**：加一个**可配的全局热键**专门用于打断。刻意不要去注册全局 Esc ——
  那会把 Esc 从所有应用手里抢走。

### F2. 没有一键导出诊断日志

- **现状**：排查全靠从终端启动 `.app` 的二进制看 stderr
  （`reportDiagnostic` → `log_frontend` → stderr）。普通用户做不到这件事。
- **证据**：v2.0.1 那四个 bug 全是靠这条通道定位的；在此之前连着两轮靠读码推测
  根因，两次都错。这个通道的价值已经证明了，缺的只是出口。
- **方向**：设置里加「导出诊断日志」—— 把最近 N 条诊断写到一个文件并在 Finder 里
  显示。注意**不能把转写内容写进去**（隐私条款：不保存聊天内容），只记事件类型与
  状态机迁移。
