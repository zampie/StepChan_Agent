# 生图与动图实践笔记

这个项目的角色素材全部由 `gpt-image-2` 生成，再经程序化处理变成可用的分层骨架；
海报、表情包、README 配图则是"模型出背景 + 真素材合成"。这份笔记记录**craft 层面**
的结论 —— 哪些事该交给模型、哪些不该，以及从生成图到可用素材中间要做什么。

流程与命令见 [`tools/poster/README.md`](../tools/poster/README.md)；
项目整体复盘见 [MAKING_OF.md](MAKING_OF.md)。

---

## 一、品牌标识不要交给生图模型

这是这个项目**最该早点想明白**的一条。角色身上有阶跃星辰的 Z 字标（发饰 + 胸前），
一开始是让模型连角色一起画出来的，结果画成了"方框套方框"—— 完全不是那个标识。
后来改成把真的 SVG 栅格化后按坐标覆盖上去。

### 问题不在提示词，在尺寸算术

Z 字标是一个圆里挖出 6 个方块。量一下 SVG：

| | 占直径比例 |
|---|---|
| 单个方块边长 | **18.3%** |
| 方块之间的间隙 | **4.3%** |

再看它在画面上的实际大小（512 画布的运行期纹理 / 1024 的原始生成图）：

| 位置 | 直径 | 方块边长 | 间隙 | 1024 原图上的间隙 |
|---|---|---|---|---|
| 发饰 | 31 px | 5.7 px | 1.34 px | 2.68 px |
| 胸前 | 17 px | **3.1 px** | **0.73 px** | 1.47 px |

**胸前那枚的方块间隙在原始生成图上只有 1.5 px，运行期纹理上 0.73 px —— 亚像素。**
这个结构在那个尺寸上物理上无法解析，换任何提示词都没用，人类插画师也画不出来。

### 即使单张画对了，一致性也过不去

带徽章的整身/整脸图有 **13 张**（基准图 + 9 个独立姿势 + 3 张整脸图），每一张都是
独立生成或独立编辑的。扩散模型不保证跨图一致 —— 标识在每张上会略有不同，
而这是个**会动的**角色：切换姿势时徽章形状跳变，比画错更明显。

### 还有一条功能性理由

发饰那枚徽章在渲染器里有**滞后抖动**（身体停下的瞬间它还在晃，系数 0.35）。
要做二级动作，它必须是独立图层 —— 画进角色图里就没法单独驱动了。

### 结论

**品牌标识是矢量资产，不是生成内容。** 正确做法是三步：

1. 从官方 SVG 出发（本项目从 8 条路径里取第 1 条，丢掉 "StepFun" 字标部分）
2. 程序化栅格化（`tools/art/logo.py`，8× 超采样，与原 SVG 的 IoU 0.968）
3. **按逐姿势实测的坐标覆盖** —— 对每张运行期纹理取"深色低饱和"连通域，
   按形状（长宽比 / 填充率）与相对基准的覆盖半径分派给发饰 / 胸前，
   每格必须恰好命中一个候选；中心取外接框中心（见 `logo.json` 的 `measured`）

第 3 步的产物是 `logo.json` 的 `placements`，它还**记录了哪些姿势下徽章看不见**
（`sleep` / `hold` 的胸前被遮住）—— 那些姿势就不贴，否则会出现一枚浮在衣服外面的徽章。

> 这个坑的代价不止画错：README 的头图和三张总览表由另一个脚本生成，**那个脚本
> 没做 logo 覆盖**，于是公开仓库里的图一直显示着模型自己画的方块。发现之后把
> 四张图全部改由同一套管线出，并删掉了那个脚本 —— 同一个事实不该有两处实现。

同理适用于：**文字**（模型渲染中文几乎必糊）、**已有角色**（模型不会画出你的角色，
会画出另一个人）。海报因此定了分工：**模型只画背景，角色用真素材，文字用真排版。**

## 二、生图接口的实测行为

接口是 `gpt-image-2`（经 models-proxy）。完整参数实测见
`~/Desktop/gpt-image-lab/docs/findings.md`，这里只记对本项目起过决定作用的几条。

### 透明背景：`generations` 能，`edits` 不能

- `generations` 侧**必须显式传 `background=transparent`**（`auto` 和不传都给 RGB 无 alpha，
  提示词里写 "cutout" 也没用），而且**只能配 `output_format=png`**
- 提示词必须是**单主体可抠图**的描述。风景类提示词配 transparent 会返回 RGBA
  但全透明像素占比 0%
- **`/images/edits` 完全忽略 `background=transparent`** —— 同样的参数、HTTP 200，
  产物却是 RGB 无 alpha

最后一条是个硬约束：本项目的所有表情/动作变体都是从 `master.png` 用 `edits` 派生的，
于是走了**纯品红幕布 + 本地抠色**（实测晕边 0.35%）。

### 主体 alpha 上限只到 253–254

模型给的"不透明"像素其实不是全不透明。严格合成场景必须自己阈值化，否则叠多层
会出现累积的半透明边。

### 画质档：`medium` 够用

同样条件下 `high` 相对 `medium` **在真实显示尺寸上看不出差别**，所以变体一律用
`medium`（master 也是）。背景这类大画面才值得上 `high`。

### 候选筛选要在真实显示条件下做

把候选缩到 **220 px** 放在**浅色和深色底**上比 —— 那才是桌宠的真实显示条件。
1024 px 全屏看上去很好的候选，缩到 220 px 后细节会糊成一团，而深色桌面上
浅蓝头发的边缘问题只有在深底上才看得见。

### `size` 的约束

宽高都必须是 **16 的倍数**，宽高比在 **1:3–3:1**，**总像素不低于约 0.66 M**，
最大 `3840x2160`。`auto` 会按提示词选画幅（实测落到 `1536x1024`），要可控就显式传。

### 返回体里的回执必须读

`background` / `output_format` / `size` / `quality` 是**服务端回执**。传了 `auto` 时
这是唯一能知道模型实际选了什么的途径 —— 不要假设。

## 三、从生成图到可用素材

生成出来的只是图，中间这几步才让它变成能驱动的骨架。

### 分层是算出来的，不是声称的

每个表情变体与 `master.png` 做**像素 diff**：

- 变化区域**紧凑**（长宽比与填充率在阈值内）→ 裁成配准覆盖层，记下 `x/y/width/height`
- **不紧凑** → 降级为整脸图交叉淡入，并**把原因写进 `rig.json` 的 `degraded`**

11 个表情里 8 个真分层，3 个（害羞 / 生气 / 难过）因为要画腮红、怒气符号、眼泪
而降级 —— 这三样散布在整张脸上，diff 区域不紧凑。

> 这份 `degraded` 列表后来反复救场：写 README 配图、做表情包、判断"哪些表情
> 能动眼睛"时，它都是直接的事实来源，而不用重新判断一遍。

### 提示词不是万能的，要承认失败并换方案

`tilt`（歪头）试过**三版提示词**都没让模型真的把头画歪：

1. 泛泛描述"歪着头"
2. 中英双写点名角度
3. 改成描述成品，并用"呆毛朝向"当硬指标

第 3 版只让呆毛倒向一侧，头和两眼连线仍是水平的，220 px 下与 `idle` 无法区分。
最后改成**渲染器对整身图做 12.6°（0.22 rad）旋转** —— 头身比 40% 的 Q 版，
整体倾斜在视觉上就读作歪头。

教训：**提示词试到第三版还不行，就该考虑换实现而不是换措辞。**

## 四、动图经验

### 能动的只有四类东西

1. 表情覆盖层（眼 / 眉 / 嘴）
2. 整身姿势图
3. 一次性效果件（闪光、爱心、zzz…）
4. 程序化变换（旋转 / 沿 y 压扁 / 上下位移）

**没有逐帧绘制的素材，也不需要。** 挥手 = 姿势图 + 小幅摆动；惊讶 = 起跳时拉长、
落地时压扁；好奇 = 歪 12.6°；兴奋 = 眼型从 `open` → `wide` → `sparkle`。

### 眼睛是表现力最强的一层，但只有分层表情能动

| 用的是 | 能不能动眼睛 |
|---|---|
| 分层表情（`layers` 模式） | **能** |
| 整身姿势图（`wave` / `sleep` 等） | 不能 —— 姿势图自带脸，覆盖层不成立 |
| 整脸图（`sprite` 模式：害羞 / 生气 / 难过） | 不能 —— 分层画不出腮红 / 怒气符号 / 眼泪 |

### 必须照搬渲染器的约束，否则配图比应用还错

这一条踩了**两次**：

- 第一次：配图脚本没照搬「覆盖层只在 `idle` 和程序化动作上成立」（`layersActive()`），
  生成的睡觉姿势被叠上表情层，**眼睛飘到了头顶**
- 第二次：表情包给 `happy` 加眨眼，而它的眼型是 `smile`（本来就是闭着的笑眼）——
  渲染器里明文写着 `NO_BLINK = {closed, half, smile}`。结果"半睁的眼"在笑眼之间
  来回，读作「无语 → 微笑」

所以：**凡是渲染器里有的约束，配图/动图管线必须照搬**，而不是"看起来差不多就行"。
现在这些参数集中列在 `tools/poster/README.md` 的对照表里。

### 眨眼节奏决定帧率

渲染器的眨眼是 `half 45ms → closed 75ms → half 55ms`（`BLINK_FRAMES`）。
10 fps 下一帧 100 ms 太粗，12 fps（83 ms/帧）下 half / closed / half 各一帧
最接近真机观感 —— **这就是表情包定在 12 fps 的原因**，不是随手选的。

### 循环必须首尾相接

贴图是无限循环播放的，首尾不接会在每轮交界处"跳"一下。所以所有振荡都写成
`sin(t/n · 2π)` 这类首尾归零的形式，而不是线性插值。

### 裁切要按整段的包围盒，不能逐帧各裁

逐帧各裁会让角色在循环时**忽大忽小地跳动**。正确做法：先算整段所有帧的 alpha
并集包围盒，再统一裁切；并且**裁成正方形**（表情包平台普遍要求等边）。

### 格式与体积：实测后选了 GIF

| 格式 | 单个体积 | 透明 | 结论 |
|---|---|---|---|
| **GIF** | 190–310 KB | 1 bit | **选它**。这个画风下看不出毛刺 |
| APNG | 570 KB–1.2 MB | 真 alpha | ffmpeg 不做帧间差分，4 倍体积换不来可见收益 |
| 动画 WebP | ~190 KB | 真 alpha | 体积好，但动画支持面不如前两者确定 |

关键是那句"看不出毛刺"是**实测**的：把同一帧分别压在浅底和深底上放大看发梢，
GIF 的 1 bit 截断没有产生可见暗环 —— 因为**角色本身带浅色描边**。
换一个没有描边的画风，这个结论可能就反了。

另外 **`dither=none`**：她是平涂画风，开抖动会在头发上留下可见纹理，而体积一样
（221 vs 222 KB）。抖动是为照片类渐变准备的，平涂画风用不上。

### 实机录屏能压多少

36 秒 / 732×1106 / **120 fps** 的屏幕录制：37.7 MB → **1.5 MB**，分辨率不动。
码率绝大部分耗在帧率上，降到 30 fps + CRF 28 就够，逐帧对比看不出差别。
投稿用的高画质档 CRF 21 也只有 3.6 MB。

**录屏前检查画面内容。** 桌宠窗是透明置顶的，录屏会把当时的桌面一起拍进去 ——
窗口标题、文件名、通知都会永久留在公开仓库里。

## 五、一句话总结

模型适合画**没有硬约束的大面积内容**（背景、角色草案）；不适合画**有精确结构
要求的小东西**（标识、文字、需要跨图一致的细节）。后者交给矢量资产 + 程序化合成，
而且要**用实测坐标对齐，不要目测**。
